## 3. Nachprüfung der bisherigen Befunde

### 3.1 `SCR-RR-B01` – S6-Liquiditätsverantwortung

**Status: geschlossen**

Die Data Pipeline Specification Version `0.4.0` definiert nun
Marktdatenqualität und das ausgewählte registrierte Gate-Profil als
verpflichtenden S6-Kern.

Regime-, Trendstärke-, Volatilitäts-, Liquiditäts- und weitere
Zustandsbedingungen dürfen nur über ein explizit registriertes und
versioniertes Gate-Profil einfließen.

Die bloße Verfügbarkeit eines Feldes erzeugt keine implizite Gate-Bedingung.

Damit besteht kein normativer Widerspruch mehr zur Regime and Gate
Specification.

### 3.2 `SCR-RR-B02` – Vermischung logischer und physischer Identitäten

**Status: geschlossen**

Die Reproducibility and Manifest Specification Version `0.3.0` trennt:

- den logisch-semantischen `build_id`;
- den logisch-semantischen `dataset_id`;
- den physischen `artifact_id`;
- den physischen `dataset_artifact_set_id`.

Physische Eigenschaften wie Byte-Hash, Dateipfad, Writerprofil,
Partitionierung und Containerlayout dürfen weder `build_id` noch `dataset_id`
beeinflussen.

Eine reine Repartitionierung oder Neuverpackung behält den `dataset_id` und
erzeugt einen neuen `dataset_artifact_set_id`.

Die Akzeptanzkriterien prüfen diese Trennung ausdrücklich. Der ursprüngliche
Blocker ist damit fachlich geschlossen.

Die Data Pipeline Specification dokumentiert die Korrekturen aus
`RCC-002-SCR-002` und bezeichnet den erneuten fokussierten Re-Review korrekt
als noch ausstehend.

Dass einzelne Arbeitsschritte durch die Erstellung des geprüften Pakets

## 4. Neue Befunde

### 4.1 `SCR-003-B01` – Review- und Freigabesequenz widerspricht der verbindlichen Pipeline

**Schweregrad: Blocker**

#### Befund

Die Spezifikationsfamilie dokumentiert an mehreren Stellen eine
Review-Reihenfolge, die von der verbindlich festgelegten RCC-002-Pipeline
abweicht.

Die verbindliche Pipeline lautet:

1. fokussierter Scientific Consistency Re-Review durch ChatGPT;
2. Architecture Integrity Review;
3. Editorial Pass;
4. Internal Certification;
5. unabhängiger Architecture Review durch Claude;
6. unabhängiger wissenschaftlicher und adversarialer Audit durch Gemini;
7. abschließende Konsolidierung und Korrektur durch ChatGPT;
8. Baseline V1 Certified;
9. Implementierung, primär mit Claude Code.

Abweichungen im geprüften Paket:

- Die Data Pipeline Specification nennt Editorial Pass vor Architecture
  Integrity Review.
- Sie fasst Claude und Gemini ohne feste Reihenfolge zusammen.
- Sie lässt Internal Certification und die abschließende
  ChatGPT-Konsolidierung aus.
- Die Reproducibility and Manifest Specification setzt Editorial Pass vor
  Scientific Consistency Review und Architecture Integrity Review.
- Sie nennt Gemini vor Claude, obwohl die verbindliche Pipeline Claude vor
  Gemini vorsieht.
- Die normative Freigabesequenz in Abschnitt 21.4 enthält weder Internal
  Certification noch ChatGPT Final Consolidation noch den expliziten
  Baseline-V1-Certified-Zustand.

#### Risiko

Reviewnachweise und Release-Gates könnten in falscher Reihenfolge erzeugt
werden.

Dadurch könnte ein Dokument als zertifiziert oder implementierungsbereit
gelten, obwohl eine vorgeschriebene Prüfstufe fehlt oder nach einer späteren
Änderung nicht erneut durchgeführt wurde.

#### Erforderliche Korrektur

Die verbindliche Pipeline muss in allen normativen und statusbezogenen
Stellen identisch eingetragen werden.

Mindestens zu korrigieren sind:

- Data Pipeline Specification: Review-Nachweis und Abschnitt 21;
- Reproducibility and Manifest Specification: Dokumentmetadaten,
  Review Evidence, Liste der ausstehenden Schritte und Abschnitt 21.4;
- alle weiteren Stellen, an denen Claude und Gemini als gemeinsame oder
  umgekehrt geordnete Review-Stufe genannt werden.

Claude- und Gemini-Status müssen bis zur tatsächlichen Durchführung
`pending` bleiben.

### 4.2 `SCR-003-B02` – Veraltete Abhängigkeitsversionen innerhalb des aktuellen Pakets

**Schweregrad: Blocker**

#### Befund

Mehrere eingebettete Spezifikationen verweisen weiterhin auf ältere Fassungen
übergeordneter oder direkt abhängiger Dokumente:

- Data Validation referenziert Data Pipeline Version `0.2.0`;
- Indicator referenziert Data Pipeline Version `0.2.0`;
- Signal Transformation referenziert Data Pipeline Version `0.2.0`;
- Regime and Gate referenziert Data Pipeline Version `0.3.0`;
- Label and Forward Return referenziert Data Pipeline Version `0.2.0`;
- Label and Forward Return referenziert Regime and Gate Version `0.1.0`;
- eine Stelle verweist weiterhin auf Reproducibility and Manifest
  Version `0.2.0`.

Im geprüften Paket sind dagegen maßgeblich:

- Data Pipeline Version `0.4.0`;
- Regime and Gate Version `0.2.0`;
- Reproducibility and Manifest Version `0.3.0`.

#### Risiko

Die Spezifikationsfamilie ist als versionierter Nachweis nicht eindeutig.

Implementierung, Review oder Manifestierung könnten sich auf eine überholte
Vertragsfassung beziehen.

Der Paket-Hash allein behebt die widersprüchlichen normativen Metadaten nicht.

#### Erforderliche Korrektur

Alle Abhängigkeits- und Überordnungsangaben müssen auf die tatsächlich im
Paket enthaltenen maßgeblichen Versionen aktualisiert werden:

- Data Pipeline: `0.4.0`;
- Regime and Gate: `0.2.0`;
- Reproducibility and Manifest: `0.3.0`;
- Data Validation: `0.1.0`;
- Indicator: `0.1.0`;
- Signal Transformation: `0.1.0`;
- Label and Forward Return: `0.1.0`.

Danach muss das vollständige Paket neu erzeugt und erneut auf veraltete
Versionsverweise geprüft werden.

### 4.3 `SCR-003-m01` – ID-Beispiel für `dataset_artifact_set_id` fehlt

**Schweregrad: Minor**

#### Befund

Abschnitt 5.1 führt `dataset_artifact_set_id` als erforderliche ID ein.

Spätere JSON-Beispiele verwenden:

```text
dataset-artifact-set:sha256:<digest>
```

In Abschnitt 5.2 fehlt dieses Format jedoch in der vollständigen Liste der
ID-Beispiele.

#### Erforderliche Korrektur

In Abschnitt 5.2 ist folgende Beispielzeile zu ergänzen:

```text
dataset-artifact-set:sha256:<digest>
```

### 4.4 `SCR-003-m02` – Unveränderlichkeitsregel ist für neue Artefaktmengen mehrdeutig

**Schweregrad: Minor**

#### Befund

Abschnitt 14.3 erklärt:

> Ein veröffentlichter `dataset_id` und seine Artefakte sind unveränderlich.

Abschnitt 5.8 erlaubt zugleich eine neue physische Artefaktmenge mit neuem
`dataset_artifact_set_id` bei unverändertem `dataset_id`.

Die beabsichtigte Semantik ist rekonstruierbar.

Die Formulierung in Abschnitt 14.3 kann jedoch so gelesen werden, als dürfe
zu einem vorhandenen `dataset_id` niemals eine neue Artefaktmenge
veröffentlicht werden.

#### Erforderliche Korrektur

Abschnitt 14.3 muss klarstellen:

- ein bereits veröffentlichter `dataset_artifact_set_id` und seine Artefakte
  sind unveränderlich;
- eine semantisch identische Neuverpackung darf denselben `dataset_id`
  behalten;
- sie muss einen neuen `dataset_artifact_set_id` erhalten;
- bestehende Artefaktmengen dürfen nicht überschrieben werden.
